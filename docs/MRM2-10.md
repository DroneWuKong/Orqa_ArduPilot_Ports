# MRM2-10 AI compatibility status

**As of 20 November 2026: build checks pass; installation and flight
compatibility with this airframe remain unqualified.** This is a dated status
for one MRM2-10 AI, not a release claim for every Orqa APB.

## What this repository builds

The `apb-copter` target builds ArduCopter 4.7.2 from the pinned source and
OrqaAPB overlay in [`upstream.lock.json`](../upstream.lock.json). The main
commit `ee71ab2` passed the [build workflow](https://github.com/DroneWuKong/Orqa_ArduPilot_Ports/actions/runs/39988602833),
including `apb-copter` and the aggregate gate. That confirms the Linux build
and artifact checks at that commit. The published `v0.1.0-rc2` firmware is
experimental and hardware unvalidated.

The APB board ID `1189` collides with upstream CORVON743V1. Verify the Orqa
USB identity `35b6:0090`, actual sensor population, bootloader and physical
axes before selecting an image; board ID alone is insufficient. The
`OrqaAPB-ICM42688` target is a different sensor-population variant.

## Fielded MRM2-10

A read-only check of the MRM2-10 on 20 November found ArduCopter 4.8.0-dev
`0922bced`, board ID `1189` and Orqa USB `35b6:0090`. This is a **different
source revision** from the build in this repository. The retained fielded
board definition differs from this overlay in IMU rotations, default logging
and optional sensor features. The exact installed application was retained
for recovery, but its original compiler and complete build inputs were not
recovered. The public `apb-copter` artifact is therefore not established as
an interchangeable update for that aircraft.

The per-airframe FC settings and tune are held in a restricted Orqa review
package. They are observed values, not board defaults, and are intentionally
not included in public firmware artifacts. A recent flight-log review found
a substantial mechanical-vibration regression; no PID change was justified
from that log. This airframe's tune and flight readiness remain **HOLD**.

## Before considering an MRM2-10 firmware update

1. Reconcile the exact fielded source, board definition, bootloader layout and
   parameter migration with the proposed image. Compare both IMU rotations
   against the actual marked chips and physical axes.
2. Preserve a complete current parameter backup, missions, logs and a tested
   exact-image recovery path. Review motor outputs, receiver, battery and
   failsafe settings against the installed wiring.
3. Run the [propellers-off acceptance checks](TESTING.md), then resolve the
   vibration finding and obtain a clean repeat log before any flight claim.

Software build success, a previous flight on another image and a settings
snapshot each answer a different question. None alone qualifies this port
artifact or the current airframe for flight.
